> **Key finding (corrects the spec):** `POST /pulls/:id/review` is **not synchronous**. `ReviewService.runReview`
> creates the `agent_runs` rows, fires `executor.executeRuns(...)` and returns `{ runs, reviews: [] }`
> immediately (`server/src/modules/reviews/service.ts:118-142`); the "(synchronous)" comment on
> `ReviewRunResponse` is stale. So `run_agent_on_pr` waits itself: start → poll `GET /pulls/:id/runs` until
> the run is no longer `running` → `GET /pulls/:id/reviews`, pick the review with that `run_id`. The executor
> inserts the review (`run-executor.ts:263`) before marking the run `done` (`:289`), so `done` ⇒ review exists.
> Still zero server changes. S10 corrects the spec.

## Goal
Claude Code in this repo gets a `devdigest` MCP server (stdio, project `.mcp.json`) with five tools:
`list_agents`, `run_agent_on_pr(repo, pr, agent)` (the only write tool — starts the review, waits, returns
`{verdict, findings[]}`), `get_findings`, `get_conventions`, `get_blast_radius` (stub → `isError`). Flat
primitive args, minified-JSON results, one-line errors naming the next step. At chat start the server costs
only its name, ≤400-char `instructions` and five tool names; budgets are enforced by tests.

- Parse at the boundary: adapter parses responses with `.pick()` views of shared contracts.
- stdout = protocol: no `console.log` / `process.stdout.write` in `mcp/src`; stderr only.
- Config only `DEVDIGEST_API_URL` (`z.string().url()`); no secrets read.
- Budgets: `instructions` ≤ 400; description ≤ 300; `tools/list` ≤ 6,000 chars; flat schemas; no
  `outputSchema` / `structuredContent` / resources / prompts / `alwaysLoad`; concise 20 findings ≤ 4,000 chars;
  every tool has `annotations`.
- No formatter; repo style by hand. Commits only on the feature branch; user pushes.

## Architecture (onion, applied to `mcp/`)
The `onion-architecture` skill is written for `server/src` + `reviewer-core` and `arch:check` does not cover
`mcp/`, so its rules are applied here by analogy and enforced by `test/architecture.test.ts` (S6).

```
mcp/src/
  core/            INNER — domain + use cases. No MCP SDK, no fetch, no process.env.
    views.ts         `.pick()` views of @devdigest/shared contracts (pure Zod) + their types
    port.ts          `DevDigestApi` interface (domain-level methods, returns views)
    errors.ts        ApiUnreachableError / ApiHttpError / ApiShapeError / ToolError + toToolMessage(err, apiUrl)
    constants.ts     instructions text, limits, severity rank, poll/progress/timeout values
    format.ts        pure: concise/full finding, filter, truncate, reviewView, conventionView
    resolve.ts       resolveAgent / resolveRepo / resolvePull (use the port)
    wait-for-run.ts  poll loop; progress via an `onProgress` callback; injected sleep/now/signal
    list-agents.ts · get-findings.ts · get-conventions.ts · run-agent-on-pr.ts
                     use cases: (deps: { api }, args, opts?) → plain result object | throw ToolError
  api/             OUTER — adapter. Implements core/port.ts with fetch; parses with core/views.ts.
    http.ts
  mcp/             OUTER — delivery edge (like routes.ts). The only place that imports the MCP SDK.
    results.ts       ok(data) → one minified JSON text block; fail(msg) → isError
    server.ts        buildServer({ api, apiUrl, wait? }): McpServer + instructions, registers tools
    tools/*.ts       one per tool: description, flat input shape, annotations, handler =
                     call ONE core use case → ok(result) | catch → fail(toToolMessage(e, apiUrl))
  config.ts        loadConfig(env) — read only by index.ts
  index.ts         COMPOSITION ROOT: config → createHttpApi → buildServer → StdioServerTransport
```

| Ring | May import | Must NOT import |
|---|---|---|
| `core/**` | `@devdigest/shared`, `zod`, own `core/*` | `@modelcontextprotocol/sdk`, `../api/**`, `../mcp/**`, `node:http`/`fetch` wrappers, `process.env` |
| `api/**` | `core/*`, shared, `zod` | `../mcp/**`, MCP SDK |
| `mcp/**` | MCP SDK, `core/*`, `zod` | `../api/**` (the adapter is injected), `process.env` |
| `index.ts`, `config.ts` | everything | — |

Rules: thin tool handlers (one use-case call, no business `if`s); use cases get narrow deps (`{ api }`),
never construct the adapter; parse at the boundary (adapter), trust inside; error *text* (the "next step")
is domain knowledge and lives in `core/errors.ts`, the edge only wraps it in `isError`.

## Tool texts (approved 2026-10-07 — use verbatim; budgets in `surface.test.ts`)
`SERVER_INSTRUCTIONS` (291 chars):
> DevDigest: local AI pull-request reviewer. Tools list reviewer agents, run a review on an imported PR and return its findings, read past findings, and read a repo's accepted coding conventions. Address PRs as repo "owner/name" + pr number. Needs the DevDigest API running (./scripts/dev.sh).

| Tool | Description | Inputs (`.describe()`) |
|---|---|---|
| `list_agents` | List the reviewer agents configured in DevDigest (id, name, model, enabled). Call this first to get a valid agent name or id for run_agent_on_pr / get_findings. | — |
| `run_agent_on_pr` | Run one DevDigest reviewer agent on an imported PR, wait until it finishes (can take minutes, paid LLM call) and return its verdict, score and findings. The only tool that writes. For an existing review use get_findings instead. | `repo` "GitHub repo as \"owner/name\"" · `pr` "Pull request number" · `agent` "Agent name or id from list_agents" |
| `get_findings` | Get the verdict and findings of DevDigest reviews already run on a PR: latest review per agent, or one run via run_id. Concise by default (WARNING+, 20 items); detail="full" adds rationale and suggestion. Does not start a review. | `repo`, `pr` · `agent?` "Only this agent (name or id)" · `run_id?` "One run, e.g. from run_agent_on_pr" · `min_severity?` enum CRITICAL/WARNING/SUGGESTION "Lowest severity to include (default WARNING)" · `detail?` enum concise/full · `limit?` "Max findings per review (default 20)" |
| `get_conventions` | Get a repo's coding conventions extracted by DevDigest (category, rule, example file). Accepted rules by default. Use them to check or write code in the repo's house style. | `repo` · `status?` enum accepted/pending/rejected (default accepted) · `limit?` "Max rules (default 20)" |
| `get_blast_radius` | Not available yet: will return the impact map of a PR (changed symbols and downstream files). Currently always returns an error — do not rely on it. | `repo`, `pr` |

## Risks
1. **zod duplication / resolution** — shared source imports `zod`, which would walk up to `server/node_modules`.
   Fix: one zod on the Zod 3 line in mcp, tsconfig `paths` + vitest alias; shared schemas only used for
   `.pick().safeParse()`, never passed to `registerTool`. If the SDK needs Zod 4 → tool schemas via `zod/v4`.
2. **Long waits** — progress notifications, 15 min cap, timeout returns `run_id` + `get_findings` hint;
   server restart reaps orphaned runs as failed.
3. **`GET /repos/:id/pulls` syncs from GitHub** — resolve once per call; documented.
4. **Response drift** — `.pick()` strip views; shape failure → clear `isError`.
5. **stdout pollution** (pnpm/tsx banners) — `--silent`, stdio test drives the real entry.
6. **`.mcp.json` cwd** — `--dir mcp` assumes repo-root cwd; use `${CLAUDE_PROJECT_DIR}` if supported.
7. **Prompt injection via findings** — data fields only, never in instructions/descriptions.
8. **pnpm install in a fresh worktree** — read the lockfile diff, delete stray `pnpm-workspace.yaml`.
